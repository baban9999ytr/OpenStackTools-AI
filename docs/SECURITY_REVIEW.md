# Pilot security review

## Implemented controls

- Staff cookies are host-only, HttpOnly, SameSite=Lax, and Secure in production. Opaque session values are HMAC-hashed in MongoDB. Users can list and revoke sessions. Password reset revokes all sessions.
- The production web image serves static assets through Nginx with an `/app` SPA fallback and same-origin `/api` proxy. Its CSP restricts scripts and connections to its own origin and limits font loading to the documented Google Fonts hosts. The sample TLS edge config is not a deployment; production HTTPS and HSTS still require operator validation.
- Registration requires email verification before login. Staff receive a 72-hour, single-use invitation link and set their own password. Reset and verification links expire after one hour. Links use a URL fragment so the token is not sent in HTTP request paths. No password is emailed.
- Dashboard mutations require the configured exact Origin and `X-Requested-With`; widget bearer sessions are bound to the site origin, assistant, organization, and visitor. Membership and role checks precede tenant-scoped queries. Cross-tenant API tests run against an ephemeral real MongoDB replica set.
- Input schemas, a 16 KB JSON limit, Helmet, and MongoDB-backed distributed request counters apply. Per-organization daily and monthly AI budgets reserve a conservative maximum before the provider call and settle measured usage afterward. Ambiguous provider failures consume the full reservation as uncertain cost; definitive rejections release it.
- Widget requests have durable unique client message IDs and a conversation processing lease. The worker retries a provider 429 once and recovers an expired lease only when no provider reservation was made. The widget keeps a 24-hour bearer session in tab-scoped `sessionStorage` and offers a clear action. This retains chat across reloads in the same tab without persistent cross-tab tracking.
- Owner-only export, retention configuration, and password-confirmed tenant deletion are available. Staff mutations write an audit record with actor, organization, route, time, and outcome, without request bodies.
- Provider calls use a 30-second timeout with SDK retries disabled and request the Standard service tier. Only a provider 429 is retried once by the queue; ambiguous timeouts and expired reserved leases are charged conservatively and not replayed automatically. A provider 404 is reported as model unavailable without replay. Usage events retain provider input/output counts and reported cached/cache-write/reasoning counts; reasoning is included in output, and missing cache breakdown uses the highest configured input price. Provider failure logs contain a controlled failure code and request ID, without raw provider error text or customer messages.
- API responses under `/api` use `Cache-Control: no-store`; `X-Request-ID` correlates structured request logs. Query strings and request bodies are omitted from routine logs, and unexpected errors are summarized without their messages. `/health/ready` returns 503 when MongoDB is disconnected.
- Production configuration rejects a non-HTTPS dashboard origin and enables Secure host-only cookies and required SMTP TLS. The staging example keeps API and MongoDB private and blocks public readiness checks; it has not been deployed.
- A separate local HTTPS Compose exercise uses a user-trusted test CA, loopback-only TLS edge, authenticated MongoDB replica set, and STARTTLS Mailpit restricted to synthetic recipients. The test CA, leaf keys, session secret, and database credentials are ignored by Git and excluded from Docker build contexts. Its public edge blocks `/health/ready`; this is local verification only.
- Phase 5 action names and arguments are strictly validated server-side. Widget mutations require a pending action, a completed originating AI request, the same origin-bound visitor session, and an explicit Confirm click. Repeated confirmations are idempotent. Existing bookings can be changed only by their visitor or authorized staff. Organization and staff opening windows are checked again at confirmation; a unique slot index prevents concurrent double bookings. Customer records require confirmation and store the consent source and timestamp. Staff configuration changes remain role-checked and audited.
- Phase 6 knowledge and listing writes use strict bounded schemas and staff roles. Widget retrieval uses fixed actions with tenant predicates and backend filters, not model-generated database queries. Only available, nonarchived listings updated within 30 days are recommended; a price ceiling requires a matching currency. Stored business text is not put in system instructions, and retrieved replies are excluded from later model context. Lead edits require a consented customer record, and assignment requires a member of the same organization.

## Remaining pilot and production risks

1. **Provider billing uncertainty:** Chat Completions usage and configured token prices produce an estimate, not an invoice. Timeout or crash may occur after a provider charge; ambiguous attempts are not replayed automatically, but a customer may choose to send a new message. The full reservation is charged internally for each uncertain attempt. Operators must reconcile provider invoices and monitor `billingStatus=uncertain`. Changing model, service tier, region, or price requires reviewing every configured rate and pilot budget. GPT-6 Luna's published long-context and service-tier modifiers are outside the pilot's bounded message sizes and explicit Standard tier; revisit this if context limits or tier policy change.
2. **Invitation delivery:** SMTP credentials and sender reputation must be configured. Mail delivery failure after registration leaves an unverified account; use the resend endpoint. Existing-email cross-organization invitations are not supported. MFA and an account recovery policy are still absent.
3. **Widget browser storage:** A same-origin site script can read its own `sessionStorage`, including the widget bearer token. Customer sites need a reviewed CSP, trusted scripts, HTTPS, and a privacy notice. A restored session is valid only for the same tab and origin; clearing site data loses it.
4. **Retention and deletion:** The daily worker removes old conversations, messages, and widget requests. Usage and audit ledgers remain until full tenant deletion. A full tenant delete runs in one MongoDB transaction and may need a staged deletion job for large tenants. Backups retain deleted data until their retention period expires. Confirm legal hold and data subject procedures before production use.
5. **Operational resilience:** MongoDB transactions require a replica set. Validate index creation, backup restore, worker behavior across multiple API instances, and failure injection on production-like infrastructure. The queue is MongoDB-backed; it is not a separate broker. Lease expiry can allow a second provider call after an unusually long response, with conservative uncertain charging.
6. **AI safety:** Tenant instructions, customer messages, and staff-entered knowledge are untrusted. Fixed retrieval tools and context exclusion reduce prompt-injection carryover, but stored text is displayed to visitors and a model can still make inaccurate free-text claims. There is no comprehensive moderation or prompt-injection evaluation. Human review remains necessary for consequential answers.
7. **Deployment:** Use TLS, exact origins, trusted proxy count, authenticated private MongoDB, a secret manager, monitored SMTP, and rate/budget alerts. Local Compose is not production hardened. Staging files are examples only; live provider delivery, a full restore, and public HTTPS behavior remain unverified. This review is engineering analysis, not a penetration test or legal opinion.
8. **Receptionist limitations:** A model can still write an inaccurate free-text scheduling claim; backend action outputs and booking state are authoritative, but prompt instructions alone do not prove freedom from hallucination. Treat this as a pilot evaluation gate. Pending proposals expire after 15 minutes; they are not slot holds, so a slot may disappear before confirmation. No external calendar sync, holiday exceptions, automated notification, identity proof beyond the origin-bound visitor session, or independent consent evidence exists. Staff changes made through the API must include an explicit confirmation flag; the dashboard uses a confirmation control. A production privacy review should cover customer contact data and action arguments in tenant exports and backups.
9. **Business data limits:** Knowledge entered by staff is public to widget visitors when retrieved; review it before publishing. Listings more than 30 days old are excluded from AI recommendations until updated, but freshness is not independently verified. Currency is required with a budget ceiling. Existing customer records from before Phase 6 may lack the new identity key and should be reviewed for duplicates before enforcing broader identity policies. The lightweight CRM does not verify customer identity or consent beyond the existing widget confirmation.
