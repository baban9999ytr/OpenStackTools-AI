# Pilot architecture

The API is Express 5 and TypeScript; the dashboard and embeddable widget are React. MongoDB stores all tenant and queue state. OpenAI is called only from the API. A fake `AIResponder` is injected into integration tests. Website and Telegram use the same conversation queue and AI orchestration. WhatsApp and Instagram remain adapter contracts and plans; neither is connected.

## Message path

A website origin registered on an assistant exchanges its public key for a 24-hour, origin-bound visitor bearer session. The widget stores that session in tab-scoped `sessionStorage`, and submits a UUID per message. MongoDB uniquely indexes `(organizationId, assistantId, visitorId, clientMessageId)`, including first messages. A transaction creates the initial conversation and request together. The request queue serializes processing through a conversation lease. A worker recovers expired leases. SDK retries are disabled; the queue retries only an explicit provider 429 once, releasing that rejected attempt's reservation. A timeout, connection failure, or expired reserved lease is charged conservatively as uncertain and is not replayed automatically. The client polls request status and conversation messages after an accepted/queued response.

Widget reads, message submissions, session creation, and confirmations use separate MongoDB-backed quotas. A broad IP abuse guard remains; authenticated reads use a per-session bucket so ordinary polling cannot spend the AI-submission allowance. The client has one serialized polling loop with `Retry-After` and bounded exponential backoff. A loopback-only dashboard preview loads the real widget with the dashboard origin, which must be on the assistant's allowed-origin list.

Before calling OpenAI, the API reserves a conservative maximum against UTC daily and monthly organization budget windows in a MongoDB transaction. For a responder that supports read-only result synthesis, the reservation includes two bounded model calls. Both windows count spent plus reserved amounts. After success, the reported usage of both calls settles the reservation; after provider uncertainty, the full reservation is charged. Limits and per-token prices are configured server-side. A separate MongoDB counter collection enforces distributed request rate limits across API instances.

## Staff path and tenant boundary

An owner registers and verifies an email. Owner-created invitations are emailed as single-use 72-hour tokens; an invitee sets their own password. Password reset tokens expire after one hour and revoke sessions. Staff sessions are opaque cookies. Every organization route validates the authenticated membership and role; queries include the organization ID. Widget conversation reads additionally require assistant and visitor IDs from the widget session. Owner-only export, retention settings, and confirmed tenant deletion are scoped to the organization. Staff mutations create audit events without request bodies.

## Current REST surface

- Auth: `/api/auth/register`, `/verify-email`, `/resend-verification`, `/login`, `/request-password-reset`, `/reset-password`, `/accept-invitation`, `/me`, `/sessions`, `/logout`.
- Organizations: members, invitations, assistants, conversations, usage, budgets, retention, paged export, and tenant deletion under `/api/organizations/:organizationId`.
- Widget: `/api/widget/sessions`, `/sessions/current`, `/messages`, `/requests/:requestId`, and `/conversations/:conversationId/messages`.
- Health: `/health/live`, `/health/ready`.

## Channel boundary and confirmations

The website session and Telegram connection resolve to a server-owned organization, assistant, visitor identity and conversation. Both call `enqueueConversationMessage`; the existing processing queue, model, tools, budget reservation and conversation lease remain shared. Telegram private messages enter through `/api/channels/telegram/:connectionId/webhook`. A configured per-connection secret header is checked before normalization. Telegram update IDs and outgoing request keys are unique per connection. Only the Telegram Bot API adapter contains provider-specific payloads. The adapter advertises text, inline-button and callback capabilities; the core action service accepts only validated action schemas.

Pending appointment and customer actions use the existing `AgentAction` transaction. Website buttons, Telegram callback tokens and unambiguous text confirmation call that same transaction. Opaque callback tokens are scoped to organization, assistant, visitor, conversation and connection, expire with the proposal, and are stored as hashes except for an AES-GCM sealed temporary inbound/outbox payload needed for retry and delivery. The callback token payload is removed after processing, delivery or terminal failure. Repeated confirmation returns the completed action without creating another booking. Natural-language approval is deliberately narrow: a bare “yes” prompts clarification. Slot occupancy and schedule are rechecked at commit.

Telegram replies are staged in a MongoDB outbox. The worker retries explicit 429 and 5xx errors with backoff. A network timeout or worker lease expiry is marked `uncertain` and is not automatically resent because the provider may already have delivered it. An operator must reconcile uncertain deliveries. Incoming text remains idempotent across webhook retries. Handoff status uses the same conversation state as website chats. The dashboard now manages self-service connections; live-provider verification remains outstanding.

## Self-service channel control plane

The authenticated Channels dashboard calls owner/admin-only organization routes. A platform-wide feature flag, public HTTPS API origin and dedicated credential encryption key are prerequisites. `getMe` verifies the pasted bot token before a tenant-owned `ChannelConnection` is created; the unique `(channel,externalAccountId)` index prevents two organizations from claiming one bot concurrently. `ChannelCredential` stores only AES-256-GCM ciphertext, nonce, tag and key ID for the bot token and per-connection webhook secret. The active key and retained previous keys live outside MongoDB. Legacy operator-managed environment references continue to resolve without migration. Responses and owner exports omit credential material.

Management operations acquire an atomic per-connection lease. A managed connection is active only after `setWebhook` succeeds and `getWebhookInfo` reports the expected centrally configured URL. Definitive provider 429/5xx responses have one bounded retry; ambiguous network errors do not. Check and repair endpoints recover a connection without allocating a second bot identity. Disable blocks ingress and stops queued output, marking sends already in progress uncertain. Disconnect additionally verifies the bot identity, removes the webhook, checks removal, and atomically removes the encrypted credential while releasing the bot identity for future binding. Reassignment starts a new conversation for that channel identity; old conversations remain in the original assistant's history. Assistant deactivation marks managed connections as needing attention.

The channel control plane does not duplicate the data plane. Telegram ingress still resolves the tenant from the server-owned connection, then uses `enqueueConversationMessage`, the same AI budget, conversation lease, action confirmation and handoff logic as the website widget. WhatsApp and Instagram need separate official business authorization and provider-specific adapters; Telegram token-paste onboarding is not reused for them.

`ChannelAdapter` declares capabilities, webhook verification (headers and optional raw request body), normalization, send and optional callback acknowledgement. The API preserves the bounded raw body for channel webhooks so a future adapter can verify a body signature before parsing it. WhatsApp and Instagram implementations must independently verify official webhook authentication and permissions, normalize events into this boundary, and handle their own interactive formats, delivery receipts, messaging windows, rate limits and retry semantics. This contract makes no claim that those APIs are enabled or that a particular button format is available.

## Phase 5 receptionist actions

The guided receptionist path uses the same queue and action transaction as model-selected actions. A bounded conversation workflow preserves a previously verified listing and requested viewing date through a focused time question, optional name collection, interruption, proposal and explicit confirmation. Staff availability is always checked by the backend; the stored proposal is revalidated at commit. Assistant personality and booking-duration settings are tenant-scoped, while platform rules and the pre-tool safety guard remain server-controlled. Appointment presentation uses verified action results and the organization's local timezone. Telegram receives plain text with simple Markdown markers removed; the website widget continues to render message text safely.

Resume and cancellation intent are routed before the model tool chooser when the visitor refers to an unfinished booking. Resume re-reads the selected listing within the tenant and rechecks the exact proposed slot; it does not treat remembered availability as a reservation. Expired or occupied proposals are revoked, while a valid pending action can be repeated without staging a second booking. General availability questions continue through the same `check_availability` action. The formatter groups only adjacent verified start times, leaving gaps visible.

Conversational Intelligence 2.0 adds a small strict interpretation/response-plan contract within this same queue. One turn can supply a booking name and ask a listing question, or correct a tentative date/time while asking for a verified price. The workflow stores the source request ID for a visitor-supplied booking name; this is temporary transactional state, not a CRM merge. Deterministic combined turns avoid another provider call. Cancellation and corrections revoke prior pending actions and tokens; a new proposal still requires backend availability and a separate confirmation. Listing searches can use a bounded set of alternative neighborhoods with the same tenant predicate. Unsupported free-text property features are stated as unverified.

The existing website message queue and budget reservation remain the entry point for model requests. The Chat Completions adapter advertises six named function tools; it treats a returned tool call as data and never runs model-supplied code. The backend validates the name and strict Zod arguments, then creates a tenant-scoped `AgentAction` keyed by the durable widget request ID. Only one function call is accepted per response. Availability is computed from configured IANA time zone, organization opening windows, staff windows, and occupied 15-minute slot claims. The backend formats availability and action results; it does not copy the model's success claim into the answer.

Booking, rescheduling, cancellation, and customer-record creation become 15-minute-expiring proposals. A visitor must explicitly confirm through the website button, a scoped Telegram callback, or an unambiguous text confirmation. Confirmation checks that the originating conversation request completed, rechecks the visitor and assistant, and runs the operation and action-state update in a MongoDB transaction. Staff use role-checked organization routes with an explicit confirmation field. Repeated action keys return the same result; changed arguments under a reused key are rejected. A unique `(organizationId,staffId,startAt)` slot index prevents simultaneous bookings. The action history omits raw arguments from the staff list response; tenant export remains owner-only. Existing human handoff state and inbox are reused.

The initial dashboard exposes appointments, a backend availability search, business hours, staff availability, customer requests, and action history. Staff schedules start closed until an owner or admin configures them. No external calendar, WhatsApp, or billing integration exists.

Widget availability requests interpret relative dates from the persisted visitor request timestamp in the organization's IANA time zone. Configurable, nonoverlapping local morning/afternoon/evening windows constrain the **database-backed availability query** before any slot is returned; organization hours, staff windows, occupied slot claims, and duration narrow it further. The visitor's explicit date and period override omitted or contradictory model arguments. Property viewings select only scheduled staff whose declared services include showings. Availability replies use local date and time without exposing the time-zone identifier and do not create appointments. Booking still requires the separate confirmed action.

## Phase 6 business data and opportunities

One `BusinessKnowledge` record per organization contains bounded public-facing profile, service/price, FAQ, policy, contact and fact fields. Owners and admins manage it. Listings are optional organization-owned structured records; staff can create, edit, archive and filter them. Widget listing retrieval uses validated backend filters, only available nonarchived records updated within 30 days, and a 10-result cap. Staff can view up to 100 nonarchived listings, including stale entries, for correction. A budget filter requires a currency, preventing cross-currency price comparisons.

An optional `listingType` marks rent or sale. Rental/sale searches require an explicit match, while legacy unclassified records remain available to generic searches until staff review. Location terms are bounded and matched independently so `Bursa Nilüfer` can match `Nilüfer, Bursa`, including common Turkish diacritic variations. Missing room metadata never satisfies a room-count filter.

The AI adapter advertises two additional fixed tools, `get_business_knowledge` and `search_listings`. The model supplies only strict arguments; the backend performs tenant-scoped retrieval. For a nonempty read-only result, the queue builds a 6 KB maximum JSON fact set with selected fields and offers one bounded synthesis call without tools. The backend accepts that prose only after grounding checks for unsupported prices, room counts, URLs and selected property attributes; otherwise it sends the deterministic formatter's reply. Transactional actions, empty results, and unsafe retrieved text stay deterministic. There is no model/tool loop. Both provider calls are metered under the same tenant budget reservation.

Retrieved business text is never added to the system instructions. Retrieval replies are excluded from subsequent model history; bounded prior search filters and tenant-scoped listing IDs support follow-ups. Stored prompt-injection text is treated as data and instruction-like text prevents the synthesis call. These checks reduce risk but cannot prove every free-text claim is grounded. Existing appointment, budget, session, and handoff controls remain active.

For listing follow-ups, the queue classifies comparison, recommendation, attribute, sort, broaden, changed-search and topic-switch intents before accepting another model-selected search. Previously shown IDs are re-read with the organization predicate and current availability/freshness rules. Recommendations can use a bounded synthesis call; attribute answers use verified current records and a deterministic missing-information response. The fallback is intent-aware, so a synthesis rejection on a recommendation does not replay the original list. Each AI request emits structured metadata including conversation/request IDs, model-selected and executed action, synthesis outcome, fallback reason, model-call count, and token counts, without message text or credentials.

The customer record adds optional requirements, budget, property preferences, lead status, assignee, staff notes, and follow-up time. Only consented records can be edited as leads. A new partial unique identity key prevents duplicate records for the same widget visitor and conversation without merging people by name or contact text. The dashboard's conversation summaries are bounded recent message excerpts, not model-generated interpretations. Owner export and tenant deletion include knowledge and listings; archived listings follow configured retention.
# Assistant model configuration

Assistant `modelSelection` is optional for backward compatibility. Missing values retain the existing server configured Chat Completions model and rates. New assistants receive a validated preset. Explicit presets and custom selections resolve through `services/model-config.ts` after platform and organization allowlists and reasoning ceilings; the selected model is then used for both tool selection and optional grounded synthesis. These profile requests use the Responses API because Terra and Sol tool calling require it. The queue reserves for both possible calls at the selected model's rates before the first provider request. The resolved model and pricing version are recorded on the request before reservation so uncertain failures retain attribution. Transactional bookings and tenant predicates remain backend controlled.

The operator allowlist defaults to Luna. Terra and Sol require explicit operator enablement after checking project access and prices. Fast/Flex/Ultrafast are not offered in tenant settings; only Standard has enabled pricing and billing policy. An organization can narrow `allowedModels` and `maxReasoningEffort` without introducing subscription names into the runtime. Profile settings are assistant scoped; organization restrictions and budget windows take precedence.


Product mode choices are Normal (Luna), Powerful (Sol), Very Powerful (Astra) and Automatic (Luna only). The product-mode resolver also requires project verification in `AI_VERIFIED_MODELS`. Existing presets, custom profiles and legacy fallback retain their previous resolution. See the README for the activation sequence.

The opt-in real-estate adapter in the shared queue keeps bounded, evidence-linked preferences and question/refusal history on the tenant-scoped conversation. Authoritative listing and availability tools resolve current stored data. Model proposals reuse the existing budgeted call and are revalidated before they can affect preferences.
