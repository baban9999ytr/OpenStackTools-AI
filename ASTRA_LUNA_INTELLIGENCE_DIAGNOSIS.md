The SDK already allowed no-tool decisions by default and disabled parallel calls. It did not force tools. Broad related tools were offered even for requests the queue could later resolve deterministically. Some names overlap in ordinary language, especially property viewing as a business service versus checking a property's actual schedule. The two advisory interpretation tools also address different workflows. Renaming them would affect fixtures and handlers, and strict typing plus explicit usage rules directly address the observed defects.

The queue reads up to 12 prior messages, excludes raw retrieval messages from history, appends the current visitor message, and maintains preferences, displayed listing order and viewing state separately in MongoDB. The old provider prompt combined historical search filters and instructions, with no explicit field-level fact/unknown or evidence-only view. Parsing accepts one bounded function call and validates JSON. Latest-turn evidence, freshness, tenant scoping, slot locks and final confirmation are server responsibilities. The benchmark's raw no-tool check measures selection only. It cannot establish a useful no-tool response. The A/B output now reports raw reference and compound-topic signals separately from customer reply and recovery metrics.

## Architecture decision

| Option | Effect on decision quality | Integration and cost | Safety and recovery |
| --- | --- | --- | --- |
| A. Improved function calling | Typed alternatives, explicit current evidence, no-tool routes, compound instructions and verified display facts | One existing call path, same tool names and handlers. Additional bounded input tokens and no new round trip. | Existing validation, confirmation, scoped actions and fallbacks apply. Historical model errors remain measurable. |
| B. Structured customer intentions | Could express multiple preferences, requested facts, schedule questions and clarifications as first-class items | New response schema and interpretation-to-action mapping. One provider call is possible, but a separate tool execution or synthesis round would add latency. Requires a separate accuracy baseline. | Every inferred state change and transaction still needs independent server evidence. Requires handling invalid, contradictory, omitted and partially actionable intents. |

Selected A. The strict preference schema uses field-specific types, with one evidence-backed entry per alternative. The real-estate provider input distinguishes final-message evidence from a bounded prior-state snapshot, preserves original display positions when a listing drops out, and separates missing deposit, fee and furnishing from zero and false. It omits contact details, names, free-text listing descriptions and evidence quotes from the snapshot. No-tool remains available and the same tool menu remains exposed in the A/B experiment. The model must still make the difficult decision. Application changes also recognize natural Turkish location alternatives and mixed spelling in furnishing questions, with separate regressions.

The API supports zero-or-one tool calling with auto choice and parallel calls disabled. The strict tool's object fields are required, additional fields are forbidden, and the typed variants are nested. Luna's Responses API publicly documents function calling and structured outputs with none and low reasoning. Project-specific strict-schema acceptance and decision quality remain unverified. [OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling) · [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) · [GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna)

Open weaknesses include whether Luna will quote only current evidence, avoid a tempting but irrelevant tool, and address the secondary intent in natural prose. A one-tool turn still relies on prose and existing server composition for independent factual and scheduling requests. The changes leave the independent booking authorization and no-guess rules in force.
