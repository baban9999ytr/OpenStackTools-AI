# Phase 4A local staging report

Date: 2026-11-07 (Europe/Istanbul). Scope: `/home/krr/Projects/OpenStackTools-AI` only. No public deployment, DNS change, remote push, purchase, production data, customer email, or main-website edit was made.

## Decision

**PASS for a repeatable local HTTPS staging exercise; NO-GO for a real-business pilot.** A production-image stack ran at `https://ai.localhost` with a Chromium-trusted, hostname-matched local certificate, loopback-only TLS edge, authenticated MongoDB replica set, and STARTTLS Mailpit. External OpenAI usage, external SMTP inbox delivery, public TLS, offsite backup, and alerts remain unverified. Local HTTPS is not proof of public production TLS readiness.

## Reused foundation and implemented changes

The existing Express API, React dashboard/widget, static Nginx image, MongoDB-backed sessions and rate limits, tenant authorization, budget transactions, account-token flows, and Phase 3 provider retry policy were retained. The default development Compose file and the parent website were not changed.

- Added `deploy/local-https/compose.yaml` with Caddy, production web/API images, authenticated MongoDB replica set, and STARTTLS Mailpit restricted to synthetic `@example.test` recipients. Only edge ports 80/443 and Mailpit UI 8026 bind to `127.0.0.1`; API, MongoDB, and web ports are private. The API has its own read/write database user. Certificate keys, replica-set keyfile, session secret, and database credentials are generated into ignored files and excluded from Docker build contexts.
- Added setup, leaf-certificate renewal, Chromium CA trust/removal, HTTPS account/security smoke, browser, and full authenticated local backup/restore scripts. Added a gated application-level live OpenAI script that can make exactly one provider request only after explicit spend and price verification flags and real local configuration. It was not run against OpenAI.
- Made `OPENAI_MAX_COMPLETION_TOKENS` configurable with a validated maximum of 800; local staging sets 64 to bound a future one-call test. The same value is used by the provider request and budget reservation.
- Fixed a Caddy route-ordering defect in both local and public-staging examples: public `/health/ready` initially reached the API; it now returns 404 while `/health/live`, `/api`, `/app`, and `/embed.js` continue to route correctly. No security check was disabled.

Local commits: `9668a8a` (local stack, configuration and route fix), `d5370d6` (cleanup failure checks), `b0bf163` (runbooks and deployment/security documentation). This report is committed separately.

## Security findings and next gates

1. Keep the local CA private key and all generated credentials in ignored files. The browser trust entry was removed after testing. A new operator can recreate and trust their own local CA through `LOCAL_HTTPS_STAGING_RUNBOOK.md`; never commit or share these files. The local MongoDB link is authenticated but not TLS-encrypted inside its private Docker network. Public staging still requires private authenticated MongoDB with TLS.
2. The application-level live OpenAI script is opt-in and sends one short synthetic message. It verifies the full persistence, usage, cost and budget path only **if it actually runs successfully against a real provider**. Provider project spending limits and application budgets must both be configured. Conservative uncertain charges after timeouts require invoice reconciliation.
3. Real SMTP verification needs a dedicated authorized mailbox and manual confirmation of inbox arrival, link origin, token expiry/reuse and failure behavior. Mailpit proved the local STARTTLS path and account flow only.
4. Before any real-business pilot, run public HTTPS and proxy checks, configure alerts and an on-call owner, rehearse a full encrypted/offsite backup restore, test multi-instance and in-flight failure recovery, review privacy/retention terms and prompt safety, and record a fresh GO/NO-GO decision. No SSO, new messaging channel, or billing feature was added.
