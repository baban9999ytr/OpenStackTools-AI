# Pilot security review

## Implemented controls

- Staff cookies are host-only, HttpOnly, SameSite=Lax, and Secure in production. Opaque session values are HMAC-hashed in MongoDB. Users can list and revoke sessions. Password reset revokes all sessions.
- The production web image serves static assets through Nginx with an `/app` SPA fallback and same-origin `/api` proxy. Its CSP restricts scripts and connections to its own origin and limits font loading to the documented Google Fonts hosts. The sample TLS edge config is not a deployment; production HTTPS and HSTS still require operator validation.
- Registration requires email verification before login. Staff receive a 72-hour, single-use invitation link and set their own password. Reset and verification links expire after one hour. Links use a URL fragment so the token is not sent in HTTP request paths. No password is emailed.
- Dashboard mutations require the configured exact Origin and `X-Requested-With`; widget bearer sessions are bound to the site origin, assistant, organization, and visitor. Membership and role checks precede tenant-scoped queries. Cross-tenant API tests run against an ephemeral real MongoDB replica set.
- Input schemas, a 16 KB JSON limit, Helmet, and MongoDB-backed distributed request counters apply. Per-organization daily and monthly AI budgets reserve a conservative maximum before the provider call and settle measured usage afterward. Ambiguous provider failures consume the full reservation as uncertain cost; definitive rejections release it.
- Widget requests have durable unique client message IDs and a conversation processing lease. The worker retries a provider 429 once and recovers an expired lease only when no provider reservation was made. The widget keeps a 24-hour bearer session in tab-scoped `sessionStorage` and offers a clear action. This retains chat across reloads in the same tab without persistent cross-tab tracking.
- Owner-only export, retention configuration, and password-confirmed tenant deletion are available. Staff mutations write an audit record with actor, organization, route, time, and outcome, without request bodies.
- Provider calls use a 30-second timeout with SDK retries disabled and request the Standard service tier. Only a provider 429 is retried once by the queue; ambiguous timeouts and expired reserved leases are charged conservatively and not replayed automatically. A provider 404 is reported as model unavailable without replay. Usage events retain provider input/output counts and reported cached/cache-write/reasoning counts; reasoning is included in output, and missing cache breakdown uses the highest configured input price. Provider failure logs contain a controlled failure code and request ID, without raw provider error text or customer messages.
- API responses under `/api` use `Cache-Control: no-store`; `X-Request-ID` correlates structured request logs. Query strings and request bodies are omitted from routine logs, and unexpected errors are summarized without their messages. `/health/ready` returns 503 when MongoDB is disconnected.
- Production configuration rejects a non-HTTPS dashboard origin and enables Secure host-only cookies and required SMTP TLS. The staging example keeps API and MongoDB private and blocks public readiness checks; it has not been deployed.
- A separate local HTTPS Compose exercise uses a user-trusted test CA, loopback-only TLS edge, authenticated MongoDB replica set, and STARTTLS Mailpit restricted to synthetic recipients. The test CA, leaf keys, session secret, and database credentials are ignored by Git and excluded from Docker build contexts. Its public edge blocks `/health/ready`; this is local verification only.
- Phase 5 action names and arguments are strictly validated server-side. Widget mutations require a pending action, a completed originating AI request, the same origin-bound visitor session, and an explicit Confirm click. Repeated confirmations are idempotent. Existing bookings can be changed only by their visitor or authorized staff. Organization and staff opening windows are checked again at confirmation; a unique slot index prevents concurrent double bookings. Customer records require confirmation and store the consent source and timestamp. Staff configuration changes remain role-checked and audited.
- Widget availability now resolves relative dates from the persisted request timestamp in the organization's zone. Explicit morning/afternoon/evening phrases override conflicting model arguments, and the backend filters slots by that local period before returning them. Property viewing requests choose only staff with a declared showing service. Empty periods return no slots and offer an alternative; availability replies no longer expose the IANA zone name. Availability checks never create bookings, and confirmation controls remain unchanged.
- Phase 6 knowledge and listing writes use strict bounded schemas and staff roles. Widget retrieval uses fixed actions with tenant predicates and backend filters, not model-generated database queries. Only available, nonarchived listings updated within 30 days are recommended; a price ceiling requires a matching currency. Read-only results may receive one bounded, tool-free model synthesis call. A selected-field fact payload, instruction-like text screen, and factual-output checks precede acceptance; deterministic formatting handles failures and transactional actions. Stored business text is not put in system instructions, and retrieved replies are excluded from later model context. Both calls are included in the budget reservation and usage ledger. Lead edits require a consented customer record, and assignment requires a member of the same organization.
- Widget polling uses a separate per-session read quota; session creation, AI message submission, and action confirmation keep independent distributed quotas plus a broad IP abuse guard. The cross-origin widget exposes `Retry-After` so it can back off without revealing raw rate-limit errors. The local dashboard preview is restricted to loopback hosts and still requires the assistant's exact allowed origin. Rental/sale searches require a matching stored `listingType`; older unclassified listings are not treated as verified rentals or sales.

## Remaining pilot and production risks

1. **Provider billing uncertainty:** Chat Completions usage and configured token prices produce an estimate, not an invoice. Timeout or crash may occur after a provider charge; ambiguous attempts are not replayed automatically, but a customer may choose to send a new message. The full reservation is charged internally for each uncertain attempt. Operators must reconcile provider invoices and monitor `billingStatus=uncertain`. Changing model, service tier, region, or price requires reviewing every configured rate and pilot budget. GPT-6 Luna's published long-context and service-tier modifiers are outside the pilot's bounded message sizes and explicit Standard tier; revisit this if context limits or tier policy change.
2. **Invitation delivery:** SMTP credentials and sender reputation must be configured. Mail delivery failure after registration leaves an unverified account; use the resend endpoint. Existing-email cross-organization invitations are not supported. MFA and an account recovery policy are still absent.
3. **Widget browser storage:** A same-origin site script can read its own `sessionStorage`, including the widget bearer token. Customer sites need a reviewed CSP, trusted scripts, HTTPS, and a privacy notice. A restored session is valid only for the same tab and origin; clearing site data loses it.
4. **Retention and deletion:** The daily worker removes old conversations, messages, and widget requests. Usage and audit ledgers remain until full tenant deletion. A full tenant delete runs in one MongoDB transaction and may need a staged deletion job for large tenants. Backups retain deleted data until their retention period expires. Confirm legal hold and data subject procedures before production use.
5. **Operational resilience:** MongoDB transactions require a replica set. Validate index creation, backup restore, worker behavior across multiple API instances, and failure injection on production-like infrastructure. The queue is MongoDB-backed; it is not a separate broker. Lease expiry can allow a second provider call after an unusually long response, with conservative uncertain charging.
6. **AI safety:** Tenant instructions, customer messages, and staff-entered knowledge are untrusted. Fixed retrieval tools, bounded synthesis facts, context exclusion, and deterministic fallback reduce prompt-injection carryover. The output guard checks selected factual categories; it cannot verify arbitrary prose or every address, staff, policy, and availability claim. Stored text can still be shown to visitors. There is no comprehensive moderation or live-model prompt-injection evaluation. Human review remains necessary for consequential answers.
7. **Deployment:** Use TLS, exact origins, trusted proxy count, authenticated private MongoDB, a secret manager, monitored SMTP, and rate/budget alerts. Local Compose is not production hardened. Staging files are examples only; live provider delivery, a full restore, and public HTTPS behavior remain unverified. This review is engineering analysis, not a penetration test or legal opinion.
8. **Receptionist limitations:** A model can still write an inaccurate free-text scheduling claim; backend action outputs and booking state are authoritative, but prompt instructions alone do not prove freedom from hallucination. Treat this as a pilot evaluation gate. Pending proposals expire after 15 minutes; they are not slot holds, so a slot may disappear before confirmation. No external calendar sync, holiday exceptions, automated notification, identity proof beyond the origin-bound visitor session, or independent consent evidence exists. Staff changes made through the API must include an explicit confirmation flag; the dashboard uses a confirmation control. A production privacy review should cover customer contact data and action arguments in tenant exports and backups.
9. **Business data limits:** Knowledge entered by staff is public to widget visitors when retrieved; review it before publishing. Listings more than 30 days old are excluded from AI recommendations until updated, but freshness is not independently verified. Currency is required with a budget ceiling. Existing customer records from before Phase 6 may lack the new identity key and should be reviewed for duplicates before enforcing broader identity policies. The lightweight CRM does not verify customer identity or consent beyond the existing widget confirmation.
## Omnichannel controls and release limits

### Self-service Telegram onboarding

Only owner/admin sessions with the existing exact Origin and `X-Requested-With` CSRF gate can create or manage a Telegram connection. Mutations have a distributed per-user rate limit and staff audit entry. Disconnect additionally verifies the staff password. The bot token is checked with `getMe`; the verified ID is unique across tenants. Managed credentials and webhook secrets use AES-256-GCM with a dedicated versioned key from the API secret environment and connection/purpose-bound authenticated data. Browser responses, tenant exports and normal logs omit token material. Key rotation requires retaining old keys until credentials are rewrapped. Existing operator-managed bindings are untouched.

The public webhook remains a separate unauthenticated endpoint protected by a per-connection secret header. It accepts messages only for active connections and active assistants. A connection becomes active only after `setWebhook` and `getWebhookInfo` agree on the configured HTTPS URL. Provider timeouts never display a success state. Disable and disconnect block new inbound messages, invalidate pending interaction tokens and stop queued output; in-flight sends become uncertain. Disconnect removes the provider webhook only after checking the bot ID and releases the bot ID locally only after confirming provider removal. Review provider account ownership, key custody, recovery from uncertain sends, backup encryption and external HTTPS behavior before enabling a real-business pilot. No live Telegram provider call has been verified in this phase.

Telegram webhooks require a per-connection secret header and an active connection whose assistant belongs to the same organization. Private chat and sender IDs must agree. Bot tokens and webhook secrets are read only from named server environment variables. Independently verify the bot account ID before binding a connection.

Callback tokens are random, hashed in the token collection, scoped to tenant, connection, conversation and visitor, and expire with the pending action. The action transaction checks the completed originating request and appointment schedule again. Unambiguous text confirmation uses the same executor; generic “yes” is insufficient. Owner export redacts token hashes and temporary callback token payloads. Full tenant deletion and configured retention include the new channel collections.

The Telegram outbox stops on uncertain network delivery and expired send leases to avoid duplicate customer messages; these require operator reconciliation. Explicit 429/5xx responses are retried with backoff. Raw text and external chat IDs are personal data and must be protected in MongoDB, backups and operations exports. Temporary callback token payloads are sealed with AES-GCM using a key derived from the server session secret; rotating that secret requires draining or invalidating pending channel deliveries. Database encryption and access controls remain necessary in production. Live Telegram delivery, webhook installation, provider account permissions and operational reconciliation have not been verified. WhatsApp and Instagram remain unimplemented.

## Local fictional demo safeguards

The optional demo seed refuses production mode and nonlocal MongoDB hosts, requires an explicit confirmation flag and private password, and uses a reserved `.test` login identity. It checks for identity and organization collisions before creating anything and uses a MongoDB transaction and marker for repeat runs. It never provisions or modifies `test@gmail.com`; a read-only lookup found that address already registered in the configured local database. The seed does not send email, make provider calls or insert synthetic usage into the real ledger. This local-only verified synthetic owner does not change the production email-verification flow. See `CONVERSATION_DEMO_REPORT.md` for test evidence and remaining limitations.
## Professional receptionist extension

The guided booking workflow is stored on the existing tenant-scoped conversation. Selected listing IDs are re-read with the organization predicate, active availability and freshness checks. Name collection is optional per assistant and is not treated as a verified external identity. A proposal is not a booking: confirmation is tied to the existing tenant/visitor/action scope, expiry, transaction and slot-claim checks. Explicit changes to date, time or listing invalidate pending proposals and callback tokens. A narrow server-side pre-tool guard prevents selected clearly operational harmful requests even if tenant instructions ask otherwise; it is not a full policy engine or a substitute for provider moderation and human review. No live-provider safety claim follows from mocked tests.

## Combined visitor turns

The strict turn interpretation is bounded and server-side. It cannot authorize a booking, choose an arbitrary tool, or alter tenant ownership. Supplied booking names carry a source request ID and live only in the conversation workflow until retention or tenant deletion. Corrections and unfinished-booking cancellation invalidate old action tokens. Listing prices come from structured tenant records; unsupported balcony/parking/elevator attributes remain unverified rather than inferred from untrusted descriptions. The existing pre-tool safety guard runs before extraction, but its keyword coverage is limited. Real-model prompt injection and conversational quality still require controlled live evaluation.
# Assistant model settings review

Model settings require an authenticated owner or admin and use the existing origin/CSRF middleware, tenant membership predicate, and staff mutation audit. The API accepts only registry model IDs and supported effort/tier combinations. Organization model and effort policy is checked at save and immediately before provider use. Legacy assistants are not silently migrated; an explicit organization allowlist can block an out-of-policy legacy model. Budget admission reserves for a primary and possible synthesis request using selected model prices. The Responses SDK has automatic retries disabled; provider timeouts remain conservatively charged as uncertain. The actual response tier is checked before measured settlement. A provider entitlement error does not trigger a paid model fallback.

Remaining controls: operator must recheck model prices and project entitlement before enabling Terra/Sol, reconcile estimated usage with provider billing, and validate live Responses tool calling in an approved low-spend project. Current UI permits Standard tier only. Cached input and cache-write breakdowns may be incomplete; the ledger conservatively prices unknown input at the highest configured input category. The model cannot authorize appointments, tenant access, or confirmation.
