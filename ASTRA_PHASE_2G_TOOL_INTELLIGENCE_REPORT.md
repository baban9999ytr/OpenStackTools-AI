# ASTRA Phase 2G tool intelligence

Phase 2G adds a scoped property-fact path, durable listing references, alternative search preferences and field-precise contact responses. The Phase 2F transcript is preserved as synthetic evidence with a source hash. The application can correct those same historical decisions offline. Fresh Luna decisions and independent Turkish review remain pending. The real-estate pilot remains **NO-GO**.

## What failed in Phase 2F

| Live call | Root cause | Phase 2G change |
| --- | --- | --- |
| 1. Greeting | Luna chose free text and the application delivered it unchanged. | Preserve free-text greetings and count a valid no-tool decision. |
| 2. Flexible intake | Luna supplied both neighborhoods and room values with verbatim evidence. Scalar state and proposal validation rejected repeated fields. The generic fallback implied a previous preference change. | Store bounded alternatives and budget uncertainty. Validate option membership against the current utterance. Ask whether the customer intends to rent or buy. |
| 3. Email and website | Lookup and reply succeeded. The exact-string grader rejected a valid Turkish paraphrase. | Validate the tool arguments strictly, then compare the requested contact-field set. |
| 4. Email only | Luna narrowed the topic to email. Business retrieval returned its whole contact card and the harness only checked for email presence. | Project the requested fields and assert field precision in retrieval and the delivered reply. |
| 5. Comparison | Luna repeated the search operation using the previous filters. The application already knew how to compare the displayed results. | Give the model a narrower search contract and preserve the grounded application comparison with visible-order references. |
| 6. Second listing's fee | Luna chose business lookup for a property attribute and reintroduced comparison. The application correctly disclosed unknown dues. | Select the persisted second displayed listing and handle its current fee in the property-fact path. |
| 7. First listing's deposit | Luna recognized the corrected listing and switched to deposit, but lacked a suitable retrieval path. | Persist the corrected listing independently of the current attribute. Read only the requested deposit. |
| 8. Transit and ownership | Luna routed both property questions to generic business knowledge. The loose category match returned an unrelated company profile. | Explain that transit time cannot be verified, withhold owner identity and clarify which listing the customer means. |
| 9. Furnishing and weekend viewing | The proposal carried old attributes forward. Generic knowledge could neither clarify the listing nor check an actual schedule. | Parse only the latest requested facts and viewing window. Ask which listing when ambiguous. With a verified listing, report the furnishing result and check an eligible consultant's availability. |

The Responses API request supplies tools, uses the provider's default tool choice and disables parallel tool calls. No tool was forced. The former business lookup description was broad and the selection set lacked property-specific retrieval. The new contract scopes business knowledge to organization information and search to fresh or changed listing filters. Recognizable property attributes have an internal handler, so they don't require a new model tool or another model call. A stable property question can still incur one model call in the existing queue. The known-listing weekend route reads the schedule directly.

## Application and schema

- The listing API accepts optional `facts.maintenanceFee`, `facts.deposit` and `facts.furnished` under the existing staff write permission. Amounts are finite nonnegative numbers in the listing currency. Zero and false are valid. Existing records need no migration. The dashboard currently preserves fields managed through the API and has no new editor for them.
- The property handler revalidates current, available, non-archived listing documents with the organization's ID. Structured staff-entered values can be displayed. A free-text mention is unverified and its content is never repeated as evidence. Missing values are disclosed, unsupported building-age and transit requests receive a limitation, and owner identity is withheld. The handler never trusts generated property IDs or copies under-specified attributes into a follow-up.
- The conversation stores up to ten displayed listing IDs in presentation order and a separate property focus ID. Explicit corrections, unique cheaper choices and an unambiguous other listing resolve against that order. An ambiguous selector prompts clarification. The appointment workflow retains its own selected listing. Requests for stale records cannot rebind an ordinal to the next current record.
- `workflow.business.alternatives` is a bounded independent set for each field. Location alternatives become an OR of token matches. Room layouts map to exact stored integers and use MongoDB membership, so 2+1 or 3+1 matches 2 or 3. Different fields still intersect. Scalar preferences from older conversations remain valid. When an explicit budget becomes unknown the limit and currency are removed and the system keeps the budget open. Updating, removing or clearing one supported field preserves the others. Existing location-order ranking is retained, with no new arbitrary preference-weighting system.
- `search_listings` now exposes `exactRooms` and `roomLayouts`; the strict server schema disallows mixing a layout list with single/minimum room constraints. Unseen interpretations still require bounded verbatim evidence. A compound intake with both sets and an open budget uses one existing budgeted interpretation call, with deterministic extraction as the validation anchor.
- The weekend viewing path requires a current property and uses the business timezone, appointment duration, business hours, eligible consultant schedules and blocked times. It offers at most three actual slots. Exact clock requests intersect the requested period. Offering a slot cannot create an appointment. Durable confirmation, revalidation, request idempotency, usage accounting, tenant isolation, handoff and premium routing policy remain in place.
- `phase2g-replay` rejects live mode before provider construction. It records the raw fixture decision, executed action and delivered reply independently. The app's response earns no raw-model credit. The historic 3/9 is unchanged.

## Operating limits

The parser handles bounded English and Turkish phrases, including the recorded failures. Arbitrary free-form preferences, ranked trade-offs, chained property references with no displayed evidence, and unsupported facts can still need clarification or staff help. Existing records without stored display order can only use the legacy snapshot; a current grounded reply records actual order going forward. Live provider behavior, broader Turkish quality and external-channel pilot operations require separate evidence.
